CodeVulFixer Documentation

An enterprise-grade VS Code Extension and Systems Orchestrator that securely ingests Dependabot alerts and GitHub CodeQL findings, analyzes blast radius, automates multi-day sprint planning, and executes verifiable fixes via Zero-Token CLIs or GitHub Copilot LM.

📖 1. Introduction & Core Value

Modern engineering teams face an overwhelming volume of vulnerability alerts across direct dependencies, transitive packages, and code-level static analysis (SAST). Resolving these manually often leads to developer alert fatigue, merge conflicts, breaking upgrades, and lack of regression safety.

⚡
Deterministic Zero-Token Repairs
Executes native package manager CLIs (npm, pnpm, yarn, uv, pip) and precompiled AST-grep structural rules without consuming AI tokens.
🤖
Copilot LM API Integration
Employs the official native vscode.lm API to leverage the developer's active GitHub Copilot instance for complex multi-layer taint refactoring.
📅
Dual-Cadence Sprint Planning
Choose between Sprint-wise (10 working days / 2-week standard Agile Scrum cycle) or Day-wise (1 working day micro-chunks) with strict cognitive caps.
🛡️
Human-in-the-Loop Intercept
Mandatory checkpoint halts the pipeline on green test runs, rendering line-by-line diffs with one-click Git SCM staging or instant rollback.

Detailed Breakdown of Each Command

1. CodeVulFixer: Open Sprint & Risk Dashboard
codevulfixer.openDashboard

How to invoke: Press Ctrl + Shift + P ➔ Type CodeVulFixer: Open Sprint ➔ Press Enter.

What it does: Reveals or creates the central interactive HTML Webview panel. If a sprint state already exists on disk in .codevulfixer/sprint-state.json, it restores the active sprint, completed items, and metric counters automatically.

When to use: Any time you want to review your repository's security posture, check multi-day sprint progress, inspect Git diffs, or modify sprint thresholds.

2. CodeVulFixer: Scan & Ingest Vulnerabilities
codevulfixer.scan

How to invoke: Press Ctrl + Shift + P ➔ Type CodeVulFixer: Scan ➔ Press Enter.

What it does:

  1. Verifies an active workspace folder is open.
  2. Inspects Git remote origin to determine owner and repo.
  3. Requests a GitHub authentication session with scopes ['repo', 'security_events'].
  4. Concurrently queries GitHub Dependabot and CodeQL Code Scanning alerts via @octokit/rest.
  5. Executes the T-Shirt Sizing Matrix (Size S, M, L) across each finding.
  6. Segments findings into multi-day sprint chunks (Day 1 Quick Wins, Day 2 Architectural, Day 3+ Hygiene).
  7. Persists state to .codevulfixer/sprint-state.json and reveals the Dashboard.

When to use: When connecting to a real GitHub repository with GitHub Advanced Security (GHAS) or Dependabot alerts enabled.

3. CodeVulFixer: Execute Current Sprint Fixes
codevulfixer.runSprint

How to invoke: Press Ctrl + Shift + P ➔ Type CodeVulFixer: Execute Current ➔ Press Enter.

What it does: Iterates through the currently active sprint (e.g. Sprint 1 Day 1) and executes the automated fix engine. For lockfile bumps, it runs package manager CLIs (npm, pnpm, yarn, uv, pip); for AST rules, it applies structural pattern fixes. After applying the mutation, it runs automated compilation and test validation suites before halting at the diff verification checkpoint.

When to use: When you are ready to batch-remediate the day's scheduled vulnerabilities.

4. CodeVulFixer: Load Realistic Demo Findings
codevulfixer.loadDemoData

How to invoke: Press Ctrl + Shift + P ➔ Type CodeVulFixer: Load Demo ➔ Press Enter.

What it does: Instantly loads 9 realistic vulnerabilities into 3 multi-day sprints and pairs them with vulnerable sample code files inside the demo/src/... directory:

  • Axios DoS (GHSA-8hc4-vh64-cxmj): Direct dependency lockfile bump.
  • Semver ReDoS (GHSA-c2qf-rxjj-qqgw): Transitive lockfile bump.
  • DOM XSS (CWE-79) in demo/src/web/render.ts: innerHTML ➔ textContent.
  • Insecure PRNG (CWE-330) in demo/src/auth/tokenGenerator.ts: Math.random() ➔ crypto.randomBytes().
  • SQL Injection (CWE-89) in demo/src/db/userRepository.ts: Parameterized SQL query.
  • Command Injection (CWE-78) in demo/src/utils/execHelper.ts: execFile argument array.
  • Path Traversal (CWE-22) in demo/src/server/fileHandler.ts: Boundary verification.

When to use: Ideal for offline development, product demonstrations, testing without GHAS credentials, or evaluating the full repair-to-SCM staging lifecycle in seconds.

5. CodeVulFixer: Reset Sprint State
codevulfixer.resetState

How to invoke: Press Ctrl + Shift + P ➔ Type CodeVulFixer: Reset Sprint ➔ Press Enter.

What it does: Deletes .codevulfixer/sprint-state.json, purges in-memory cached sprints, resets all telemetry metrics to zero, and updates the open dashboard to the empty state.

When to use: When you wish to wipe previous sprint records and perform a clean re-scan or test a new sprint partition.

🔐 4. Module A: Secure Authentication & Alert Ingestion

Authentication is achieved without any hardcoded credentials or third-party tokens by tapping into VS Code’s native vscode.authentication infrastructure.

ℹ️
Required Scopes: repo and security_events. These scopes allow querying GitHub Advanced Security (GHAS) APIs for both Dependabot alerts and CodeQL Code Scanning alerts.

Git Remote Resolution Flow

  1. Queries git config --get remote.origin.url within the active workspace.
  2. Parses standard HTTPS (https://github.com/owner/repo.git) and SSH (git@github.com:owner/repo.git) URLs.
  3. Extracts owner and repo metadata and resolves the current working branch via git rev-parse --abbrev-ref HEAD.

Unified Data Ingestion & Automatic API Pagination

Standard GitHub API queries cap single-page responses at 100 items. CodeVulFixer implements automated full-pagination via octokit.paginate across both Code Scanning and Dependabot endpoints, guaranteeing that all pages of vulnerabilities are collected without truncation: 

// Full-pagination queries across all pages of alerts (bypasses 100-item cap)
const dependabotAlerts = await octokit.paginate(
  octokit.rest.dependabot.listAlertsForRepo,
  { owner, repo, state: 'open', per_page: 100 }
);

const codeScanningAlerts = await octokit.paginate(
  octokit.rest.codeScanning.listAlertsForRepo,
  { owner, repo, state: 'open', per_page: 100 }
);

Local State Retention on Re-Ingest

When you run "Ingest & Scan" again, CodeVulFixer preserves your local remediation progress:

  • Fix Status Retention: Findings previously marked applied, verified, or in_progress in .codevulfixer/sprint-state.json maintain their status, applied diffs, zero-token resolution engines, and hours saved metrics. You never have to manually re-mark them.
  • Historical Audit Preservation: If a resolved finding was closed on GitHub and is no longer returned in open alerts, CodeVulFixer keeps it in the local state copy so your audit trail is not erased.
  • Zero-Token Local Verification: Immediately after ingestion, CodeVulFixer automatically scans your local files (package.json and source AST) to verify if any pending findings have already been resolved on disk with 0 AI tokens.

📐 5. Module B: Impact Analysis & T-Shirt Sizing Matrix

Before scheduling work, CodeVulFixer inspects code context, package topologies, and data-flow graphs to assign each finding a rigorous T-Shirt Size:

Size Risk Level Estimated Effort Evaluation Criteria Fix Automation Candidate
Size S Low Risk ~0.5 Hours Direct lockfile patch bumps, transitive deduplications, or self-contained localized SAST fixes (e.g., innerHTML ➔ textContent). Yes (Zero-Token Eligible)
Size M Medium Risk ~1.5 – 2.5 Hours Major package upgrades with non-breaking usage, or SAST findings embedded in secondary non-critical business modules. Copilot LM with Human Review
Size L High Risk ~3.5 – 5.0 Hours Single-major API migrations (v1 ➔ v2), critical application paths, or complex security weaknesses (SQL Injection, Command Injection, SSRF). Manual Intercept Mandatory
Size XL High Risk (Epic) ~54 – 96 Hours Multi-generational major version leaps (ΔMajor ≥ 2, e.g. Spring 1.x → 5.x). Involves architectural rewrites, XML-to-annotation migration, MVC modernization, and platform constraints. Architectural Epic

Multi-Major Version Distance Multiplier (ΔMajor ≥ 2)

Standard vulnerability engines treat all major version bumps identically. CodeVulFixer calculates the actual version delta between current and target versions: 

const majorGap = Math.max(1, targetMajor - currentMajor);
if (majorGap >= 2) {
  size = 'XL'; // Escalate to Architectural Epic
  estimatedHours = Math.min(96, Math.round(16 * Math.pow(1.5, majorGap - 1)));
}

For a 4-generation leap (e.g. Spring Framework 1.2.9 → 5.3.39), the engine automatically scales the estimate to 72.0 hours, partitioning the migration into an Architectural Sprint Epic.

Technology-Specific Sizing & Effort Heuristics

CodeVulFixer dynamically identifies the underlying software stack from project build manifests (CMakeLists.txt, pom.xml, .csproj, Cargo.toml, go.mod, package.json) and target file extensions, applying tailored sizing multipliers:

Technology Ecosystem & Manifests Sizing Behavior Architectural Rationale
C / C++ .cpp, .c, .h, CMakeLists.txt, vcpkg Min Size M/L (~3.5h–6.0h) Unmanaged native memory: requires AddressSanitizer (ASAN) audits, Valgrind leak tests, and multi-compiler ABI validation (MSVC/GCC/Clang). Automated commits disabled for safety.
Delphi / Pascal .pas, .dpr, .dproj Min Size M (~3.0h) Unmanaged memory pointers, COM interop, absence of standard automated package managers. Requires manual boundary verification.
.NET / C# .cs, .csproj, packages.config Contextual (S to XL) Target framework boundaries (e.g. net48 ➔ net8.0 is Size XL). Evaluates assembly binding redirects and app.config migrations.
Java / Spring / Apache .java, pom.xml, build.gradle ΔMajor Scaled (S to XL) Bytecode target limits (Java 8 vs 17), javax.* ➔ jakarta.* namespace breaks, and XML bean-to-annotation migration.
PowerShell .ps1, .psm1 Scriptblock Analysis Evaluates Invoke-Expression script injection, execution policy bypass, and [CmdletBinding()] validation.

📅 6. Module C: Dual-Cadence Sprint Planning Engine

Instead of dumping hundreds of alerts into a flat unstructured backlog, CodeVulFixer introduces a flexible Dual-Cadence Planning Engine that aligns remediation with either standard 2-week Scrum sprints or daily focused micro-chunks:

Standardized 10-Day Agile Sprints
⏱️ 10 Days / 60h Capacity
Duration: 10 working days per sprint (Standard 2-week Agile / Scrum cycle).
Velocity Standard: 1 developer working day = 6 hours (60 hours total capacity per sprint).
Dynamic Capacity Allocation: Sprints are calculated by taking total estimated hours across all findings and partitioning sequentially: 
sprintCount = Math.max(1, Math.ceil(totalEstimatedHours / 60));
  • Track 1 (Priority 1): Dependabot dependency upgrades & manifest locking scheduled first.
  • Track 2 (Priority 2): Code Scanning SAST refactorings & AST transforms scheduled next.
  • Strict Mathematical Equality: The sum of sprint hours strictly and precisely equals the summary total hours.

⚡ 7. Module D: Dual-Engine Repair System

1. Deterministic Zero-Token Engine

For dependency lockfiles and known AST structural patterns, background child processes execute exact native commands:

  • npm install <pkg>@<version> --package-lock-only
  • pnpm update <pkg>@<version>
  • yarn up <pkg>@<version>
  • uv add <pkg>==<version>

For SAST code vulnerabilities, precompiled ast-grep structural rewrite rules apply safe code transformations:

1
// CWE-79: DOM XSS AST Rewrite
2
- userBioElement.innerHTML = user.bio;
2
+ userBioElement.textContent = user.bio;
1
// CWE-330: Insecure Randomness AST Rewrite
2
- const token = Math.random().toString(36).substring(2);
2
+ const token = require('crypto').randomBytes(24).toString('hex');

2. AI-Assisted Copilot LM Engine

For complex taint-flow issues (e.g. SQL Injections or shell command interpolations), the engine dispatches a focused security prompt to the user's active Copilot instance via vscode.lm.selectChatModels({ vendor: 'copilot' }).

🛡️ 8. Module E: Validation & Human-in-the-Loop Intercept

No fix is trusted blindly. Every mutation must clear a rigorous multi-stage local validation check:

1. Compilation Check
Executes npm run build or tsc --noEmit. Verifies zero syntax or type breakages.
2. Regression Tests
Monitors npm test / pytest using vscode.tasks. Captures execution duration and stack traces.
3. Security Advisory Audit
Re-runs npm audit to ensure the target CVE/GHSA advisory has completely cleared.
4. Collateral & Cascading Vulnerability Audit
Validates whether bumping the target package introduces new transitive CVEs or violates peer dependency requirements. Halts pipeline if collateral risks are detected.

Mandatory Checkpoint Overlay

When tests pass, the automation pauses and renders the interactive Checkpoint Banner in the Diff Inspector:

👍
[👍 Mark as Verified & Stage for Check-in]: Automatically executes git add <file> and populates the SCM commit message:
security(fix): [CodeVulFixer] resolved [ID] in [Context]
❌
[❌ Reject Fix & Rollback]: Executes git restore <file> to revert workspace mutations, marks the finding as rejected, and updates sprint tracking metrics.

🧩 10. Module G: Smart Compatibility Advisor & Platform Guard

Security fixes cannot exist in a vacuum. Upgrading a package to the latest release often introduces catastrophic runtime incompatibilities or collateral vulnerabilities. CodeVulFixer’s CompatibilityAdvisor actively detects platform constraints and calculates safe intermediate compromises.

1. Platform Deadlock Detection: The Spring 1.x → 5.x / Java 8 Case Study

The Scenario: A critical Remote Code Execution vulnerability in Spring Framework demands an upgrade. An advisory might recommend upgrading to Spring 6.x. However, a legacy submodule in your repository requires Java 8 for compatibility with proprietary dependencies or removed JVM APIs (CORBA, JAXB, Unsafe).

💡 CodeVulFixer Smart Compatibility Guard Active
Target Ideal: Spring 6.1.14 (Mandates Java 17+) ➔ Selected Safe Target: Spring 5.3.39 (Java 8 Compatible)
Dependency Constraint: Legacy module banking-legacy requires Java 8; Spring 6+ mandates Java 17+.
Tradeoff Analysis: Upgrading to Spring 6.x causes fatal JVM runtime deadlock. Upgrading to Spring 5.3.39 remediates critical RCEs (Spring4Shell) while ensuring 100% Java 8 runtime compliance.
🛡️ Risk Reduction Profile: Critical RCE mitigated to Zero with zero platform failure risk.

2. Apache Log4j: Resolving Log4Shell on Java 8

The Scenario: Critical Log4Shell Remote Code Execution (CVE-2021-44228) requires upgrading org.apache.logging.log4j:log4j-core. Upstream advisories suggest latest 2.20+ or 3.x. However, these versions require Java 9+ bytecode, whereas the enterprise build uses Java 8.

💡 Apache Log4j Safe Intermediate Target
Target Ideal: Log4j 2.20.0 (Mandates Java 9+) ➔ Selected Safe Target: Log4j 2.17.1 (Java 8 Compatible)
Dependency Constraint: Workspace pom.xml specifies <java.version>1.8</java.version>.
Tradeoff Analysis: Upgrading to 2.20+ fails bytecode compilation on Java 8. Upgrading to 2.17.1 completely neutralizes Log4Shell while running cleanly on Java 8.
🛡️ Risk Reduction Profile: Critical Log4Shell RCE neutralized with zero JVM bytecode conflict.

3. Apache log4net: Resolving XML Entity RCE on .NET Framework 4.8

The Scenario: Legacy .NET enterprise application targets <TargetFramework>net48</TargetFramework> with log4net 1.2.10, vulnerable to XML External Entity Injection (CVE-2018-1285). Upstream major releases (3.x) require modern .NET Core / .NET 6+ and break app.config XML parser sections.

💡 Apache log4net Safe Intermediate Target
Target Ideal: log4net 3.0.0 (Modern .NET Core / .NET 6+ Required) ➔ Selected Safe Target: log4net 2.0.15 (.NET Framework 4.8 Compatible)
Dependency Constraint: .csproj is pinned to net48 with legacy assembly binding redirects.
Tradeoff Analysis: Upgrading to 3.x breaks XML logging layouts and runtime bindings. Upgrading to 2.0.15 fixes CVE-2018-1285 while preserving 100% backward compatibility with .NET Framework 4.x.
🛡️ Risk Reduction Profile: High XXE & RCE neutralized with zero .NET framework runtime migration risk.

4. Collateral & Cascading Vulnerability Interception

When upgrading a dependency, CodeVulFixer checks if the upgrade would introduce downstream peer dependency collisions or new transitive CVEs:

  • Peer Middleware Collisions: Example: Upgrading express from 4.x to 5.0 introduces breaking router signatures that break existing cookie-parser and body-parser modules. CodeVulFixer recommends safe intermediate 4.19.2.
  • Automated Pipeline Intercept: If a package bump introduces a cascading vulnerability, the automated verification engine halts, marks the status as failed, and presents the safe alternative version in the terminal failure diagnostic.

🧩 11. Module H: Root-Cause Consolidation, Co-Remediation & Learned Patterns

In enterprise codebases, raw vulnerability alerts (e.g., 50 Dependabot alerts and 30 CodeQL findings) rarely represent 80 separate problems. Instead, multiple CVEs routinely stem from the exact same vulnerable package, and multiple code scanning alerts belong to the same CWE category across adjacent modules.

🎯
Root-Cause Consolidation Metric
CodeVulFixer automatically calculates the Remediation Leverage Ratio (Total Raw Alerts ÷ Total Unique Root-Causes). A ratio of 2.1x means resolving 7 unique root issues completely eliminates 15 raw security alerts.
⚡
Approach 1: Cascading Co-Remediation (0-Token)
When a single package upgrade fixes multiple vulnerabilities (e.g., axios 0.21.1 ➔ 1.7.4 fixes SSRF and ReDoS), fixing one finding automatically cascades zero-token resolution across all co-dependent alerts upon local validation.
🧠
Approach 2: Local Repository Pattern Learning
Once AI resolves a recurring vulnerability (e.g., CWE-89 SQL injection prepared statements), CodeVulFixer records the abstract AST repair transform into .codevulfixer/learned-patterns.json. Future matches are fixed deterministically with 0 AI tokens.

1. Automated Vulnerability Clustering Engine

Upon ingesting security alerts, the ClubbingEngine groups findings into two distinct cluster taxonomies:

  • Package Dependency Clusters (Dependabot): Identifies all alerts sharing the same packageName and target manifest file (e.g., package.json or pom.xml). When one vulnerability in the cluster is upgraded to a safe version, all peer vulnerabilities in the same package are scheduled for zero-token resolution.
  • CWE Security Query Families (CodeQL): Aggregates static analysis findings by CWE rule family (e.g., CWE-89 SQL Injection, CWE-79 Cross-Site Scripting, CWE-22 Path Traversal). When an AI repair successfully passes regression tests, the diff pattern is extracted and stored for zero-token reuse.

🔧 14. Troubleshooting & FAQ

Q: GitHub Authentication fails or reports Insufficient Scopes?

Ensure your GitHub account has access to GitHub Advanced Security (GHAS) or repository security events. Re-authenticate by running the command: CodeVulFixer: Scan & Ingest Vulnerabilities. If evaluating on a private repository without GHAS, use the built-in "Load Demo Data" button to test all sprint and repair workflows.

Q: How does CodeVulFixer prevent upgrade deadlocks (e.g., Spring 1.x ➔ 5.x on Java 8)?

The CompatibilityAdvisor parses Maven pom.xml (<java.version>, maven-compiler-plugin source/target) and package.json engines to detect active runtime locks. When an unconstrained major upgrade (such as Spring 6.x) requires a higher runtime (Java 17+) than the workspace supports or causes peer dependency conflicts, the advisor calculates the highest safe intermediate target (e.g., Spring 5.3.39). This eliminates the critical security vulnerabilities while ensuring 100% platform and module compatibility.

Q: How does the Zero-Token lockfile bump work without installing heavy dependencies?

The engine passes the --package-lock-only flag to npm install, which updates purely the dependency resolution graph in package-lock.json without downloading extraneous tarballs, completing in under 2 seconds.

Q: How can I reset the sprint state back to fresh?

Run CodeVulFixer: Reset Sprint State from the command palette or click the "Reset" button in the dashboard header. This cleans up .codevulfixer/sprint-state.json.
